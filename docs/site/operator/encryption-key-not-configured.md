# Sharko's encryption key is missing or changed

This page is for when Sharko will not start because `SHARKO_ENCRYPTION_KEY` is missing, or when
Sharko can no longer read the connections and personal Git tokens it saved before.

**How urgent:** Fix it now. With no key, Sharko does not start at all. With a changed key, Sharko
runs but has lost its Git and ArgoCD connection until you put the old key back or enter the
connection again.

Before you start, set up the shell variables from [First checks](troubleshooting.md#set-up-once).

Sharko uses one encryption key for everything it saves in encrypted form: the Git and ArgoCD
connection (in the `sharko-connections` Secret), each user's personal Git token, and the AI
settings. The Helm chart makes a random key on the first install and keeps it in the chart's own
Secret (named `sharko` when the release is called `sharko`, otherwise `<release>-sharko`), under
the key `SHARKO_ENCRYPTION_KEY`. The pod gets it from there as an env var. It is not a Helm value.

## What you see

### The key is missing

The pod never becomes ready and keeps restarting. The log of the run that stopped ends with:

```text
SHARKO_ENCRYPTION_KEY is required when running on Kubernetes. It is auto-generated by the Helm chart on first install.
```

### The key changed

Sharko starts, but the log shows the saved connection can't be read:

```json
{"level":"WARN","msg":"[startup] no active connection","error":"... decrypting connections: decryption failed (wrong key?): ..."}
```

The UI acts as if no connection was ever set up. Users who saved a personal Git token see this when
they press **Test** in **Settings > My Account**:

```json
{"error": "decryption failed: decrypting token: decryption failed (wrong key?): ..."}
```

### Sharko runs outside Kubernetes with no key

This only happens when you run `sharko serve` on your own machine. Saving or testing a personal Git
token answers HTTP 500 with:

```json
{"error": "encryption key not configured"}
```

The routes are `PUT /api/v1/users/me/github-token` (save) and
`POST /api/v1/users/me/github-token/test` (test). Everything else keeps working. On Kubernetes you
never see this answer, because there Sharko does not start without the key.

## Why it happens

- **Someone removed the key from the Secret,** or replaced the whole Secret by hand without it.
- **The key was made again.** The chart only keeps the old key when Helm can look at the live
  Secret during an upgrade. When the chart is rendered with `helm template`, or by ArgoCD or another
  GitOps tool, Helm can't look, so every render makes a new random key. The next sync writes that
  new key over the old one, and nothing saved with the old key can be read any more.
- **Sharko was reinstalled** (uninstall, then install) without keeping the old Secret.
- **Outside Kubernetes**, nobody set `SHARKO_ENCRYPTION_KEY` before running `sharko serve`.

## How to fix it

1. **Check the key is in the Secret.** This shows only the key names, not the values:

   ```sh
   kubectl -n "$SHARKO_NS" get secret sharko -o json | jq '.data | keys'
   ```

   You should see `SHARKO_ENCRYPTION_KEY` in the list.

2. **If the key is missing, and nothing was saved yet** (a new install), let the chart make a new
   one. Run your usual `helm upgrade` with the same chart version. The chart adds a key when the
   Secret has none. Then restart Sharko:

   ```sh
   kubectl -n "$SHARKO_NS" rollout restart deploy/sharko
   ```

3. **If the key is missing or changed, and you have the old key** (from a backup of the Secret, or
   from your Git history if you keep the rendered Secret there), put it back and restart:

   ```sh
   kubectl -n "$SHARKO_NS" patch secret sharko --type merge \
     -p '{"stringData":{"SHARKO_ENCRYPTION_KEY":"<the old key>"}}'
   kubectl -n "$SHARKO_NS" rollout restart deploy/sharko
   ```

   The key can be any length. A pod only reads the key when it starts, so the restart is needed.

4. **If you do not have the old key**, what was saved with it is gone. Start again with the new key:

   - Delete the `sharko-connections` Secret (or the name you set in `config.connectionSecretName`),
     restart Sharko, then enter the Git and ArgoCD connection again in **Settings > Connection**
     or with `sharko connect`.
   - Each user who had a personal Git token clears it and saves it again in
     **Settings > My Account**. Clearing works even with the wrong key
     (`DELETE /api/v1/users/me/github-token`).
   - Enter the AI settings again, if you use them.

5. **If ArgoCD or another GitOps tool installs Sharko**, stop it from making a new key on every
   sync. Tell it to leave the `SHARKO_ENCRYPTION_KEY` field of the `sharko` Secret alone (in ArgoCD,
   an `ignoreDifferences` entry for that field, with the `RespectIgnoreDifferences=true` sync
   option). Otherwise this page will happen again at the next sync.

6. **Outside Kubernetes**, set the env var before you start Sharko, and keep using the same value:

   ```sh
   export SHARKO_ENCRYPTION_KEY='<a long random string you keep safe>'
   sharko serve
   ```

Keep a copy of the key somewhere safe outside the cluster, for example in your password manager.
Without it, a lost Secret means entering every connection and token again.

## How to check it's fixed

- The pod is `Running` and `READY 1/1`, and the log shows `server initialization complete`.
- The log shows the connection was read:

  ```sh
  kubectl -n "$SHARKO_NS" logs deploy/sharko --since=10m | grep '\[startup\] active connection found'
  ```

- A user with a personal Git token presses **Test** in **Settings > My Account** and gets a good
  answer. With the API, `POST /api/v1/users/me/github-token/test` answers HTTP 200 with
  `"status": "ok"`.

## If that didn't work

Open an issue at <https://github.com/MoranWeissman/sharko/issues>. Include:

- the Sharko version (`sharko version`, or the `version` field from `/api/v1/health`)
- the log lines from the last hour that mention `SHARKO_ENCRYPTION_KEY`, `decryption failed` or
  `[startup]`
- the output of step 1 (key names only, never the key itself)
- what you tried from this page

Never paste the key, a token or the data of a Secret into an issue.
