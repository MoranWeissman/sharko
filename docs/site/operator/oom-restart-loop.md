# Sharko keeps restarting

This page is for when the Sharko pod restarts again and again. Most of the time it is one of two
things: the pod runs out of memory, or Sharko stops itself at start because something in its
settings is wrong.

**How urgent:** Fix it now. While the pod restarts, the UI and the API go up and down, and the
background jobs that keep clusters in step never finish a pass.

Before you start, set up the shell variables from [First checks](troubleshooting.md#set-up-once).

## What you see

- The pod shows `CrashLoopBackOff`, or the `RESTARTS` number keeps going up:

  ```sh
  kubectl -n "$SHARKO_NS" get pods -l app.kubernetes.io/name=sharko
  ```

- **Out of memory:** the last time the container stopped, Kubernetes wrote `OOMKilled` as the
  reason, and the exit code is `137`:

  ```sh
  kubectl -n "$SHARKO_NS" get pods -l app.kubernetes.io/name=sharko \
    -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.status.containerStatuses[0].lastState.terminated.reason}{" "}{.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}{end}'
  ```

- **A startup error:** the exit code is `1`, and the log of the run that stopped ends with an
  `Error:` line. Common ones:

  ```text
  SHARKO_ENCRYPTION_KEY is required when running on Kubernetes. It is auto-generated by the Helm chart on first install.
  <NAME> is not a Sharko setting. Did you mean <OTHER NAME>? Sharko has not started: ...
  <NAME> is not a Sharko setting. Sharko has not started: ... Remove it, then start Sharko again
  failed to create K8s connection store: ...
  load catalog trust policy: ...
  load curated catalog: ...
  could not set up the initial admin user (and Sharko refuses to run without auth): ...
  could not load persisted API tokens (running on would risk losing them): ...
  ```

- **The health check fails:** `kubectl describe pod` shows `Liveness probe failed` events. Both
  probes call `/api/v1/health`. If that page does not answer three times in a row, Kubernetes
  restarts the container.

## Why it happens

- **The pod runs out of memory.** The chart sets a memory limit of `512Mi` by default. A large
  fleet, many addons or many catalog sources can need more than that. When the pod goes over the
  limit, Kubernetes stops it and starts it again.
- **A setting is wrong, so Sharko stops itself at start.** Sharko checks its settings before it
  serves anything. If something it needs is missing or broken, it prints the reason and stops on
  purpose. Restarting does not help until you fix the setting. Examples:
    - the encryption key is missing (see [encryption-key-not-configured.md](encryption-key-not-configured.md))
    - an env var that starts with `SHARKO_` is not a real Sharko setting, often a typo
    - Sharko can't read or write its own Secrets in its namespace
    - a catalog file or trust setting given through `extraEnv` can't be read
- **Sharko crashed while running.** A bug in Sharko or in one of its background jobs stops the
  whole program. The log of the run that stopped shows `panic:` near the end.
- **The health check is too strict for a slow node.** If the node is very busy, `/api/v1/health`
  can take longer than 3 seconds to answer.

Things that do NOT make Sharko stop at start: ArgoCD being down, Git being down, or no connection
set up yet. Sharko starts and shows those problems in the UI.

## How to fix it

1. **Read the log of the run that stopped.** `--previous` shows the run before the current one:

   ```sh
   kubectl -n "$SHARKO_NS" logs deploy/sharko --previous | tail -50
   ```

   If it ends with an `Error:` line, go to step 3. If it ends with `panic:`, go to step 4.
   If it ends with no error at all and the reason is `OOMKilled`, go to step 2.

2. **Give the pod more memory.** Find your chart version, then raise the limit and keep the same
   version:

   ```sh
   helm -n "$SHARKO_NS" list
   helm upgrade sharko oci://ghcr.io/moranweissman/sharko/sharko \
     -n "$SHARKO_NS" --reuse-values --version <your chart version> \
     --set resources.limits.memory=1Gi
   ```

   If ArgoCD or another GitOps tool installs Sharko, change `resources.limits.memory` in the values
   file in Git instead. A change made by hand on the cluster is undone at the next sync.

   Only add memory. Do not run more than one Sharko pod: Sharko must always run as one single pod.

3. **Fix the setting that the `Error:` line names.**

   - Encryption key missing: follow [encryption-key-not-configured.md](encryption-key-not-configured.md).
   - "is not a Sharko setting": look at the env vars on the pod, and fix or remove the name. If you
     set it through the chart, it is in `extraEnv`.

     ```sh
     kubectl -n "$SHARKO_NS" get deploy sharko \
       -o jsonpath='{range .spec.template.spec.containers[0].env[*]}{.name}{"\n"}{end}'
     ```

   - "failed to create K8s connection store", "initial admin user" or "persisted API tokens": Sharko
     can't read or write its own Secrets. Check that the chart's RBAC is turned on (`rbac.create`)
     and that the Role and RoleBinding the chart makes for this exist (`sharko-auth` when the
     release is called `sharko`):

     ```sh
     kubectl -n "$SHARKO_NS" get role,rolebinding | grep auth
     ```
   - "load catalog ...": fix or remove the catalog setting you added through `extraEnv`. See
     [catalog-sources.md](catalog-sources.md) and [catalog-trust-policy.md](catalog-trust-policy.md).

   Then let the pod start again, or restart it:

   ```sh
   kubectl -n "$SHARKO_NS" rollout restart deploy/sharko
   ```

4. **If it is a `panic:`**, save the last 100 lines of the previous log. This is a bug in Sharko.
   Upgrading to the newest release may already fix it. If not, open an issue with those lines (see
   below).

5. **If only the health check fails on a slow node**, give it more time with the chart keys
   `livenessProbe.timeoutSeconds` and `livenessProbe.failureThreshold`. Do this only after you have
   ruled out the other causes.

## How to check it's fixed

- The pod shows `Running`, `READY 1/1`, and the `RESTARTS` number stops going up for at least
  10 minutes.
- Sharko answers:

  ```sh
  curl -s "$SHARKO_URL/api/v1/health" | jq
  ```

  A good answer has `"status": "healthy"` and your Sharko version.
- The log shows `server initialization complete` once, and no new `Error:` or `panic:` lines.
- If you raised memory, watch how much the pod uses for a day. `process_resident_memory_bytes` from
  Sharko's `/metrics` page, or `kubectl top pod`, should stay well under the new limit.

## If that didn't work

Open an issue at <https://github.com/MoranWeissman/sharko/issues>. Include:

- the Sharko version (`sharko version`, or the `version` field from `/api/v1/health`)
- the last 100 lines of `kubectl logs deploy/sharko --previous`
- the reason and exit code from the first step under "What you see"
- what you tried from this page
